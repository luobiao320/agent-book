## 1. 工具的五类划分

## 核心结论
工具可以按交互方向和作用对象理解为五类：感知、执行、协作、事件触发、用户沟通。

## 五类工具
- 感知：搜索、读文件、查数据库，获取信息。
- 执行：写文件、运行命令、调用业务 API，改变世界。
- 协作：委托子 Agent 或请求人类参与。
- 事件触发：由邮件、定时器、Webhook 等外部事件启动 Agent。
- 用户沟通：主动向用户发送消息、邮件、语音等。

## 为什么分类有价值
不同工具的风险和设计重点不同。感知工具关注信息量和噪声；执行工具关注安全与幂等；事件工具关注重复投递和状态恢复；沟通工具关注频率、授权和渠道。

## 2. 工具设计：粒度、描述与参数

## 核心结论
工具不是“API 原样暴露给模型”。一个好工具需要为模型重新设计名称、能力边界、描述、参数和错误返回。

## 粒度
过细会迫使模型进行大量机械编排；过粗则难以组合和控制。应围绕一个稳定、可解释的能力单元设计。

## 描述
描述要回答：什么时候用、输入是什么、返回什么、有什么限制。参数名应语义明确，枚举能用就不要依赖自由文本。

## 参数保真
模型生成的参数在经过 Harness、序列化和后端适配时不能被偷偷改写。尤其是 SQL、正则、代码、文件路径等高保真参数，应避免不必要的二次自然语言处理。

## 演进
工具契约一旦进入 Prompt 就类似公开 API，需要版本意识、兼容性和回归测试。

## 3. MCP 与大规模工具生态

## 核心结论
MCP 等协议降低了工具接入成本，但“能连接很多工具”不等于 Agent 就能正确使用它们。工具越多，选择问题越严重。

## 大规模工具的挑战
把数百个 schema 全部塞进上下文会消耗 token、稀释注意力并增加误调用概率。因此需要工具目录、搜索、分类、动态加载等机制。

## MCP 的角色
协议解决发现、描述和调用的标准化接口；真正的生产质量还取决于权限、认证、错误语义、限流和业务适配。

## 设计原则
把“工具协议”和“工具产品设计”分开思考：协议统一传输方式，工具本身仍要有清晰的人机语义。

## 4. 感知、执行与协作工具

## 感知工具
目标是给 Agent 足够信息，又不过量。搜索和文件读取通常应支持分页、范围读取、摘要或二阶段展开。

## 执行工具
错误代价更高，应优先考虑幂等、dry-run、权限、审计、超时和回滚。对于删除、支付、部署等操作，工具应尽可能专用且参数严格。

## 协作工具
让 Agent 把任务委托给其他 Agent 或人类。关键不是“再启动一个模型”，而是定义清晰的任务边界、输入产物、返回契约和超时机制。

## 工程原则
工具输出也属于上下文的一部分。返回内容应面向下一步决策设计，而不仅仅是把后端原始响应全部倾倒给模型。

> 来源章节：https://bojieli.github.io/ai-agent-book/book/chapter4/

## 5. 事件驱动与异步 Agent

## 核心结论
很多真实任务不是一次请求内完成：等待邮件、审批、定时任务、Webhook、长时间执行都需要 Agent 跨时间继续工作。因此 Agent Runtime 必须支持事件驱动和持久状态。

## 关键问题
- 事件可能重复投递：需要幂等。
- Agent 可能重启：需要持久化检查点。
- 多事件并发：需要任务隔离和一致性策略。
- 等待期间用户可能改变目标：需要可取消和可打断。

## 同步模型如何异步工作
模型本身仍然是一轮一轮同步推理；异步性由 Harness 提供。事件到达时重新加载任务状态，构造新的上下文，再让模型继续决策。

## Java 类比
更接近消息队列 + Saga/工作流引擎，而不是一个长时间阻塞的 HTTP 请求。

## 6. 主动工具发现与 Skill 渐进披露

## 核心结论
当工具数量很大时，可以让模型先“发现”工具，再加载详细 schema，而不是永久把所有定义放进上下文。

## 两层结构
第一层只提供工具/Skill 名称、用途、类别等轻量索引；模型确认需要后，再读取完整文档或工具定义。

## Skill 的作用
Skill 可以把“该找哪些工具、怎样组合、有哪些业务约束”一起封装，从而让工具发现从纯 schema 搜索升级为任务能力发现。

## 收益
减少上下文长度、提高缓存稳定性、降低错误选择，并让能力模块可以独立发布和测试。

## 风险
发现机制本身也可能漏召回，因此需要默认核心工具、搜索兜底和可观测的召回日志。
