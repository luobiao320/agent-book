## 1. Pass@k、Pass^k 与过程指标

## 核心结论
Agent 评估不能只有一个“成功率”。不同指标回答不同问题：Pass@k 关注多次尝试中至少成功一次的能力上限；Pass^k 更关注连续多次都成功的可靠性。

## 业务视角
演示一个 Agent 时，“偶尔能做成”就很惊艳；部署到生产时，用户更关心“每次都能做成”。因此能力上限和可靠性必须分开测。

## 过程指标
最终失败并不能告诉你哪里坏了。还应记录工具选择正确率、步骤数、重试次数、违规动作、时间、成本等过程信号。

## 安全与鲁棒性
需要单独覆盖越权、提示注入、异常工具返回、网络失败和脏数据等场景，而不是只用干净 happy path。

> 来源章节：https://bojieli.github.io/ai-agent-book/book/chapter6/

## 2. 自动评估环境

## 核心结论
Agent 的评估对象不是一段文本，而是“模型 + Harness 在环境中完成任务的行为”。因此需要可重复、可重置、可验证的评估环境。

## 基本组成
任务描述、初始环境状态、可用工具、成功判定器、超时规则、运行日志和重置机制。

## 工具调用型环境
适合代码、文件、数据库等可程序验证任务。理想判定器直接检查最终世界状态，而不是只看 Agent 自己声称“完成了”。

## 人机交互型环境
当任务涉及用户偏好和澄清，需要模拟用户或真实评审。模拟器本身也会引入偏差，因此要区分被测 Agent 与评估环境的模型。

> 来源章节：https://bojieli.github.io/ai-agent-book/book/chapter6/

## 3. 评估任务数据集设计

## 核心结论
Benchmark 的质量首先取决于任务分布，而不是评分脚本。任务过于模糊、简单或与真实流量脱节，会产生漂亮但无用的分数。

## 设计维度
- 描述是否明确但不泄露答案。
- 难度是否有层次。
- 结果是否可客观验证。
- 是否覆盖真实用户分布和高风险长尾。
- 是否避免训练/测试污染。

## 数据质量
失败样本要人工复核：究竟是 Agent 错、任务描述错，还是环境坏。评估集应持续吸收线上 bad case，但要防止“只优化旧题”造成过拟合。

> 来源章节：https://bojieli.github.io/ai-agent-book/book/chapter6/

## 4. LLM-as-a-Judge 与失败归因

## LLM-as-a-Judge
当结果难以用规则判断时，可以让模型按 rubric 评分。但 Judge 也会有偏好、位置效应和随机性，因此应提供清晰标准，必要时使用多次评判或人工校准。

## 失败归因
比“最终失败”更有价值的是找到轨迹中第一个关键错误：错误搜索、误读结果、参数错误、编辑失败、过早结束等。

## 轨迹回归
可以固定前半段轨迹，只测试某个关键决策点，形成 prefix regression。这样能把复杂端到端问题拆成可重复的局部能力测试。

## 工程价值
失败归因把 Benchmark 从排行榜工具变成开发工具：每一种失败类型都可以对应 Prompt、工具、模型或 Harness 的改进方向。

> 来源章节：https://bojieli.github.io/ai-agent-book/book/chapter6/

## 5. 评估驱动的模型选型与成本

## 核心结论
模型选型应在自己的 Agent Harness 和任务集上做，不要只看通用排行榜。不同模型在工具调用、长上下文、遵循格式、延迟和价格上的行为差异很大。

## 成本拆分
不仅有 token 价格，还包括平均轮数、工具调用成本、失败重试、缓存命中、长任务占用时间等。一个单次调用便宜但经常绕路的模型，端到端可能更贵。

## 选型方法
建立候选模型矩阵：成功率、可靠性、P95 延迟、平均成本、安全指标。再根据业务优先级做权衡。

## 持续迭代
模型版本变化时应自动跑回归集，避免“看起来更强的新模型”悄悄破坏现有 Agent 行为。

> 来源章节：https://bojieli.github.io/ai-agent-book/book/chapter6/

## 6. 统计显著性与可观测性

## 核心结论
Agent 有随机性，小样本上从 70% 提升到 74% 可能只是噪声。需要置信区间、重复运行和足够样本量来判断改动是否真的有效。

## 可观测性
线上每次任务应记录结构化轨迹：模型版本、Prompt/Skill 版本、工具参数、工具结果摘要、token、延迟、错误和最终结果。

## 为什么重要
没有版本化和轨迹，就无法回答“这个失败是模型升级导致，还是工具服务异常？”也无法把线上问题稳定复现到评估环境。

## 原则
评估与可观测性应该使用同一套核心事件模型，让离线 Benchmark 与线上真实流量能够互相映射。

> 来源章节：https://bojieli.github.io/ai-agent-book/book/chapter6/

## 7. 消融、A/B 测试与特性开关

## 消融实验
一次只移除或改变一个组件，观察性能变化，用于理解某个 Prompt、Skill、工具或压缩机制的真实贡献。

## A/B 测试
用于在线验证“新方案对业务目标是否更好”。实验设计要区分机制指标（如工具错误率）和最终目标（如任务完成率、用户满意度）。

## 特性开关
生产 Agent 需要能按用户/任务/流量快速启停新 Prompt、模型、工具和策略。最好同时具有发布开关与实验分组能力。

## 工程原则
每个“智能改进”都应该能被测量、灰度、回滚。否则 Agent 系统会变成不可解释的 Prompt 堆栈。
