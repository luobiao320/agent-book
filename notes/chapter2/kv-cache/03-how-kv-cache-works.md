# 03｜KV Cache 是怎么工作的

## 没有 KV Cache 时

假设上下文已经有 1000 个 token，模型现在准备生成第 1001 个 token。

如果没有缓存，模型需要重新处理前面 1000 个 token 的 Attention 中间结果。

接着生成第 1002 个 token 时，又要重新处理前面 1001 个 token。

随着文本增长，这种重复计算会越来越重。

## 有 KV Cache 时

第一次处理前缀时，模型会计算并保存历史 token 在每一层里的 K/V。

后续每生成一个新 token：

1. 只计算新 token 的表示；
2. 得到这个 token 的 K/V；
3. 把新的 K/V 追加到已有缓存；
4. 当前 Query 直接和缓存里的历史 K 做 Attention；
5. 利用缓存里的 V 得到输出。

可以粗略理解为：

```text
第一次：
[A][B][C]
 ↓  ↓  ↓
缓存 K/V

下一步生成 D：
缓存：[A][B][C] + 新计算 [D]

下一步生成 E：
缓存：[A][B][C][D] + 新计算 [E]
```

重点是：**旧内容尽量不重算，新内容不断追加。**

## Prefill 和 Decode

推理过程经常被拆成两个阶段。

### Prefill

模型先一次性读取完整输入 Prompt，并计算所有初始 token 的 K/V。

这个阶段计算量通常比较大，但并行度高。

### Decode

进入逐 token 生成阶段后，每一步只生成一个新 token，并复用已有 KV Cache。

这个阶段更依赖缓存读取效率。

## 为什么长上下文更依赖缓存

上下文只有几十个 token 时，重复计算可能还不明显。

但如果 Agent 上下文已经达到几万 token，重新计算整个历史前缀就会非常昂贵。

因此，长上下文系统里常见的重要优化目标包括：

- 尽量复用历史前缀；
- 减少无意义的上下文改写；
- 控制缓存占用；
- 做分页式或分块式 KV Cache 管理。

## 最关键的理解

KV Cache 优化的不是“模型记忆能力”，而是：

> **模型在生成过程中对历史上下文的重复计算。**
