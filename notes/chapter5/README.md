## 1. 为什么 Coding 是通用 Agent 的基础能力

## 核心结论
代码不仅是一种输出形式，也是 Agent 的“元能力”：它能把自然语言意图转成精确、可执行、可验证的程序，并在运行时组合出原本不存在的工具。

## 基础工具面
一个实用 Coding Agent 通常围绕目录浏览、搜索、读取、编辑/写入、命令执行等少量通用能力构建。工具不一定多，但组合空间很大。

## 为什么通用
代码可以做数据转换、调用 API、生成文档、处理媒体、自动化浏览器、构造 UI。相比为每个长尾任务预先写专用工具，代码让 Agent 在受控沙箱里即时创造适配器。

## 前提
通用性扩大攻击面，因此代码执行必须配合隔离、资源限制、文件权限和网络策略。

## 2. Coding Agent 的闭环与 Harness

## 核心结论
Coding Agent 的核心不是“一次生成完整代码”，而是工程闭环：理解需求 → 搜索相关代码 → 小步修改 → 运行测试/检查 → 根据错误继续修复。

## Harness 的价值
Harness 管理工作目录、命令执行、上下文、工具输出截断、超时、测试结果和 Git 状态，让模型能像开发者一样持续获得反馈。

## 好的执行习惯
- 修改前先定位相关代码。
- 尽量局部编辑，减少无关改动。
- 改完立即运行最相关验证。
- 报错后基于真实输出定位，不凭想象重写。
- 最终检查 diff 和测试结果。

## 判断标准
Coding Agent 的质量更多体现在“闭环恢复能力”，而不仅是首轮生成的代码是否漂亮。

## 3. 搜索、编辑与错误恢复

## 搜索
代码库很大时，先用文件名、符号、文本搜索缩小范围，再读取局部文件。把整个仓库塞入上下文通常既贵又低效。

## 编辑
工具可提供整文件写入、字符串替换、patch 等不同方式。精确编辑有利于减少 diff，但对匹配条件更敏感；失败时应读取当前文件状态再重试。

## 错误恢复
工具失败是正常路径，不应被视为异常终止。Agent 需要看到可操作的错误信息，例如命令、退出码、stderr、冲突位置。

## 工程原则
让失败“可诊断”。如果工具只返回 `failed`，模型就只能猜；如果返回具体上下文，Agent 才能建立修复闭环。

## 4. Coding Agent 的安全边界

## 核心结论
代码执行能力非常强，因此安全模型必须默认不信任模型生成的代码。最小权限和隔离应该由运行时实现。

## 关键措施
- 使用容器/沙箱隔离执行。
- 限制可访问的工作目录。
- 网络默认关闭或按域名白名单。
- 设置 CPU、内存、时间和输出上限。
- 敏感凭据通过受控工具代理，而不是直接写入环境。
- 危险命令和生产操作需要额外确认。

## 防 Prompt Injection
仓库里的 README、issue、网页内容都可能包含恶意指令。读取到文本不代表它获得更高权限，真正的动作权限必须由 Harness 决定。

## 5. 代码作为思考工具、规则与适配器

## 代码作为思考工具
对于数学、数据、复杂逻辑，代码可以把模糊推理变成可执行验证。例如计算、排序、约束求解和数据统计都适合让程序给出客观结果。

## 代码作为业务规则
当规则可以形式化时，写成函数、校验器或状态机通常比把几十条自然语言约束都交给模型更可靠。

## 代码作为系统适配器
Agent 可以临时写脚本转换数据格式、批量处理文件或封装陌生 API，把一次性需求变成可执行工具。

## 原则
模型适合处理模糊判断，代码适合执行确定逻辑。两者结合比让任一方承担全部职责更稳定。

## 6. 生成式 UI 与 Agent 自举

## 核心结论
当 Agent 会写代码时，它不仅能调用已有界面，还能生成新的交互界面、可视化和辅助工具。这意味着“工具集合”不再完全由开发者预先决定。

## 生成式 UI
模型可以根据当前任务动态创建表单、图表、报告页面，让用户更高效地确认参数和查看结果。

## 自举
Agent 可以发现重复操作后编写脚本或 Skill，把一次性的解决方案固化成后续可复用能力。长期来看，这与持续进化机制相连。

## 风险
自动生成并持久化的新工具必须经过测试、权限审核和版本管理。能够创造工具，不代表能够绕过工具治理。
