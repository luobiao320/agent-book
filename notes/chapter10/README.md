## 1. 多 Agent 的两个核心维度

## 核心结论
理解多 Agent 可以先看两个维度：是否共享上下文，以及协作拓扑是什么。不要只根据“用了几个模型实例”判断架构。

## 上下文
共享上下文的 Agent 能看到相同历史，协作简单但容易互相干扰、上下文快速膨胀。不共享上下文则隔离更强，需要显式通信和产物交接。

## 拓扑
可以是管理者—工作者、对等协作、链式、树形或去中心化网络。不同拓扑决定信息传播、控制权和失败扩散方式。

## 工程原则
先从任务依赖关系出发选拓扑，而不是为了“多 Agent”而多 Agent。

## 2. 什么时候多 Agent 真正优于单 Agent

## 核心结论
多 Agent 的价值通常来自并行、上下文隔离和角色制衡，而不是简单把同一个模型复制几份。

## 适合场景
- 子任务相互独立，可以并行。
- 不同子任务需要大量互不相关的上下文。
- 需要独立审核，避免同一条思路自我确认。
- 专家能力或权限天然分离。

## 不适合
任务高度串行、共享状态复杂、通信成本大于并行收益时，多 Agent 反而更慢、更贵、更难调试。

## 判断公式
拆分收益 = 并行收益 + 隔离收益 + 专业化/制衡收益 − 通信成本 − 协调成本 − 错误传播成本。

> 来源章节：https://bojieli.github.io/ai-agent-book/book/chapter10/

## 3. 共享上下文与隔离上下文

## 共享上下文
多个角色操作同一消息历史，交接成本低，但上下文膨胀快，而且一个 Agent 的噪声会污染其他 Agent。

## 隔离上下文
每个 Agent 拥有自己的上下文，通过文件、消息或结构化产物通信。这更像真正的进程/服务隔离。

## 文件系统作为黑板
文件可以成为多 Agent 的共享外部状态：计划、数据、草稿和结果都落盘。好处是可审计、可复用；风险是并发写冲突和版本覆盖。

## 工程原则
共享“结果”，少共享“全部思考过程”。跨 Agent 交接应有明确 artifact 契约，例如 JSON、Markdown 报告、patch 或任务状态。

> 来源章节：https://bojieli.github.io/ai-agent-book/book/chapter10/

## 4. 协作模式：审核、辩论、头脑风暴与管理者

## 提议者—审核者
一个 Agent 产出方案，另一个独立检查。适合代码审查、合规和事实核验。

## 辩论
多个 Agent 提出不同论据，再由裁判汇总。适合高不确定问题，但容易产生大量重复 token。

## 头脑风暴/专家小组
强调多样性，先并行产出不同方案，再聚合。价值来自独立视角，而不是角色提示写得多花哨。

## 管理者模式
Manager 拆分任务、分配 Worker、汇总结果。适合依赖清晰的复杂任务，但 Manager 可能成为瓶颈和单点故障。

## 原则
让不同 Agent 获得真正不同的信息、权限或任务，才能产生有效互补。

## 5. 多 Agent 的典型失败模式

## 并发冲突
多个 Agent 同时编辑共享文件，会覆盖内容或基于过期状态工作。需要锁、分支、版本号或合并协议。

## 错误级联
上游 Agent 的错误结论被下游当成事实，层层放大。交接产物需要证据、置信度和独立验证。

## 循环失控
Agent 互相委托或反复审核可能永不终止。需要最大深度、预算、轮数和终止条件。

## 理解债
子 Agent 过度依赖其他 Agent 的摘要，会逐渐失去对原始问题的理解；审核者可能“认知投降”，默认前人的结论。

## 工程原则
多 Agent 首先是分布式系统问题，其次才是 Prompt 角色扮演问题。

## 6. Agent 社会与长期多主体系统

## 核心结论
当大量 Agent 长期互动时，研究对象从单次协作扩展到社会：形成关系、声誉、制度、竞争与经济行为。社会模拟可以研究复杂涌现现象。

## 长期状态
每个 Agent 需要身份、记忆和资源；环境需要时间推进、事件和规则。没有持久状态，就只是一次性的群聊。

## 经济与博弈
资源稀缺、信息不对称和利益冲突会产生策略行为。评价不能只看单个 Agent 是否“聪明”，还要看系统稳定性、公平性和激励兼容。

## 工程启示
未来 Agent 网络可能像今天的微服务和组织一样，需要身份、权限、信誉、协议和市场机制。A2A 等协议解决通信标准，但社会治理仍是更大的问题。
